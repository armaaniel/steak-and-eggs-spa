What Wealthsimple does: They define Service Level Objectives (SLOs) for "Critical Flows" (e.g., the Order Flow or Login). If the error rate exceeds the "error budget" for a 5-minute window, it triggers a Datadog monitor which pages Rootly.

* How you can grow: Build a dashboard or an automated script that calculates your SLO. E.g., "99.9% of /graphql requests involving MarketService.buy must complete in < 500ms." If your Trace table shows you dipping below that, have your app trigger a Slack webhook.

1. Synthetic Monitoring (Testing "Critical Flows")
The Problem: Your server returns a 200 OK, and CPU is low, so your monitors say everything is fine. But a database lock is preventing users from actually executing a trade. You don't find out until a user complains. What WS Does: Wealthsimple relies on Datadog Synthetics. These are automated scripts that run every 5 minutes from the outside world. They actually spin up a headless browser (or hit the API), log in as a test user, execute a dummy trade, and verify the portfolio balance updated. They call these "Critical Flows." High Impact for You:
* Write a simple script (e.g., in GitHub Actions running on a cron schedule, or a free tool like BetterStack) that hits your production /login endpoint, gets a JWT, hits /deposit, and verifies the response.
* If this script fails, it pages you. This proves your app actually works, not just that the server is turned on.

2. Idempotency & Resilient Queues (Handling Money Safely)
The Problem: Your ingester container fetches a stock price, starts creating Transaction records for users with limit orders, and halfway through, the ECS task crashes or runs out of memory (OOM). When ECS restarts the task, does it accidentally execute those trades twice? What WS Does: Fintechs obsess over idempotency and Dead Letter Queues (DLQs). If an upstream provider (like their market data vendor) times out, the background job must retry safely without duplicating data. I see DeadJobException and Connection reset errors all over their incident logs. High Impact for You:
* Add Idempotency Keys to your GraphQL mutations (e.g., MarketService.buy). Ensure that if a client sends the exact same buy request twice because of a network stutter, your database only processes it once.
* If you use Sidekiq or GoodJob for background processing, implement a robust retry mechanism and a DLQ. If a job fails 5 times, it should be moved to a dead queue where you can manually inspect it, rather than just vanishing.


4. The "One-Minute Rollback"
The Problem: You merge a PR. GitHub Actions builds the Docker image and deploys it to ECS. 2 minutes later, your synthetic monitors start failing. The app is broken. What do you do? If you have to write a fix, commit it, and wait for CI to rebuild the Docker image, your app is down for 10+ minutes. What WS Does: Wealthsimple's deploy documentation explicitly references "Rollbacks and Redeployments for Incidents." They have a mechanism to instantly revert to the previous container image without waiting for a rebuild. High Impact for You:
* Create a "Rollback" GitHub Action. It shouldn't build any code. It should just take a git commit hash, find the corresponding Docker image tag that already exists in your AWS ECR, and update the ECS task definition to point back to that old tag.
* Being able to press a button and have your app back online in 30 seconds while you investigate the bug locally is a massive operational superpower.


3. ECS Event Lifecycle ChatOps (Catching "OOMKills")
The Wealthsimple Context: In a March incident, a WS engineer was paged by Rootly for an "Infrastructure Pod OOM Kill" (Out Of Memory). Container orchestration systems (like Kubernetes or ECS) will silently kill and restart containers that use too much RAM. The Problem: If your ingester container has a memory leak, ECS will kill it and restart it. You might never notice, because it keeps trying to run. But under the hood, your data ingestion is constantly being interrupted. 🌱 High-Impact Implementation:
* Set up an AWS EventBridge rule that listens for ECS Task State Changes (specifically looking for STOPPED tasks with the reason OutOfMemory or exit codes other than 0).
* Route that EventBridge trigger to an SNS topic or a simple Lambda function that posts to your personal Slack/Discord.
* You will instantly get a message: "⚠️ ECS Task 'ingester' was killed due to OutOfMemory." This gives you x-ray vision into how AWS is treating your containers.

3. Edge-Level Load Shedding (Protecting the Compute)
The SRE Concept: Your steakneggs app is currently exposed to the open internet via the ALB. What happens if a botnet decides to brute-force your /login endpoint with 10,000 requests per second? What WS Does: WS doesn't let garbage traffic reach their Ruby containers. As I saw in their incident logs, when malformed requests slip through, they cause application-level 404s/500s that waste expensive CPU cycles. 🌱 High-Impact Implementation:
* Attach an AWS WAF (Web Application Firewall) to your Application Load Balancer via Terraform.
* Implement Rate Limiting. Tell the WAF: "If a single IP address hits /login more than 50 times in a 5-minute window, return a 429 Too Many Requests error at the Load Balancer layer."
* This is called "Load Shedding." It drops malicious or abusive traffic at the network edge, ensuring your expensive ECS containers (and Postgres connection pool) are reserved exclusively for legitimate users.

1. Automated "Smoke Tests" (Testing)
The Wealthsimple Context: In their operational reviews, WS grades services on "Criterion 5.4: Smoke Tests." A unit test proves your code works in isolation. A smoke test proves your app actually works when deployed to AWS. 🌱 High-Impact Implementation:
* Add Playwright or Cypress to your repository.
* Write a single, end-to-end (E2E) test: It opens a browser, hits your frontend, logs in, deposits $1,000, buys 1 share of AAPL, and asserts the portfolio value updated.
* Configure your GitHub Action so that after it deploys to ECS, it automatically runs this Smoke Test against your live production (or staging) URL. If it fails, the deploy is considered botched.
2. Structured Error Tagging (Observability)
The Wealthsimple Context: In the July 27 AI Summary, WS noted a massive observability gap: "565 GraphQL query exception errors this week have no @error.message or @error.kind populated. GQL failures are untriageable without this." The Problem: Your notification.rb captures the duration of a GraphQL request, but if a user submits a bad trade, you just get a generic HTTP 500 or a raw stack trace in Sentry. You can't easily filter by "Which ticker symbol caused the error?" 🌱 High-Impact Implementation:
* Update your Sentry and telemetry setup to use Structured Context/Tags.
* When a user makes a request, inject tags into the Sentry scope: user_id, graphql_operation, ticker_symbol, and error.kind (e.g., InsufficientFundsError).
* This allows you to go into Sentry (or your logs) and say: "Show me all errors today where error.kind == InsufficientFunds AND ticker_symbol == TSLA." This is how enterprise engineers debug complex issues in seconds.
3. Load Testing to Prove Your Telemetry (Testing + Telemetry)
The Problem: You have this beautiful notification.rb telemetry setup and AWS ECS scaling rules, but you don't actually know how they behave under extreme stress until it happens in real life. 🌱 High-Impact Implementation:
* Write a load testing script using a tool like k6 (by Grafana).
* Configure the script to simulate 500 concurrent users logging in and requesting portfolio data over 60 seconds.
* The Goal: Run the script against your ECS cluster and watch your telemetry. Does your DB CPU spike to 100%? Do your duration metrics in your Trace table jump from 50ms to 4,000ms? Do your ECS tasks autoscale? Load testing validates that your telemetry actually works when you need it most.
